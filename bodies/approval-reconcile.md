Before: if Hermes asked for an approval while Conduit was reopening the chat (after a reconnect, or right after a new chat starts), and that reopen failed, the approval was thrown away with everything else Conduit had held back during the reopen. Hermes announces an approval once and then waits, so the chat never showed the card: the lock screen said "Waiting for your approval", tapping Review opened a chat with no Run or Reject. Separately, answering a card whose session Hermes no longer knows ("session not found") showed "Hermes did not accept that decision" and an error banner, which reads like Hermes refused the answer.

After: a failed reopen still draws the approval, clarify and input cards it received (and applies their withdrawals, in order) before showing its error. Streamed text is not replayed; the next reopen reads it back as before. A "session not found" answer to `approval.pending` or `approval.respond` marks the card "This approval is no longer active." with no banner.

How: the `catch` of the preserve-current reconcile calls `replayBufferedDecisionPrompts(for:)` before it sets `.reconnecting` and settles. That replays only `.approval`, `.approvalWithdrawn`, `.clarify`, `.clarifyExpire`, `.inputPrompt` and `.inputPromptExpire` from the reconciliation's buffer through `applyStreamEvent`, while the reconciliation's accepted ids still route them to the open chat; it runs before `.reconnecting` so the prompt's running edge doesn't hide the failure state. `legacyApprovalTarget(for:using:profile:)` maps `HermesClient.isSessionNotFoundError` to `.noLongerPending`, and the `approval.respond` catch treats it as expired. No new strings.

Found on a real device: an App Store build (2.1.0, build 216) paired with push, on an agent with Manual approvals. The approval push arrived on the locked phone, but the chat never drew the card, and a second device's Run and Reject both came back "Hermes did not accept that decision" inside the timeout. A new chat whose stored id isn't saved yet answers the reopen with "session not found", which is when the buffered card was lost.

Review notes: this doesn't change which id a new chat's reopen uses (it still tries the durable id first and fails until the gateway has saved it); that is a separate fix. "Session not found" means this connection no longer has the card's runtime, so the answer can't reach the request from here; "no longer active" is the honest reading for this device, and the card can no longer be retried into the same error.
