Before: `SystemVoiceAudioSession` made every AVAudioSession call on the main actor. When the last audio owner let go (a conversation ends, Read Aloud stops, dictation finishes), `setActive(false, .notifyOthersOnDeactivation)` ran on the main thread. That call blocks until audio I/O stops, so the UI froze for it and the main-thread-unresponsiveness diagnostic fired. Stop-then-listen-again also deactivated and immediately reactivated the session, briefly letting other apps' audio come back.

After: all session changes go through one serial queue, and deactivation is queued without the main thread waiting. Activation, category changes and the speaker override still wait for their result, because callers need the error and a live session before starting an engine; being on the same queue, they always run after any deactivation queued before them, so a stop can never land after a newer start. A deactivation still queued when a newer change arrives is dropped, so stop-then-listen-again keeps the session up.

How: a small `VoiceAudioSessionBackend` protocol wraps the raw `setCategory` / `setActive` / `overrideOutputToSpeaker` calls (`SharedAVAudioSessionBackend` in the app, a fake in tests). `SystemVoiceAudioSession(backend:queue:)` owns the serial queue and an `OSAllocatedUnfairLock` generation counter: every change except deactivation bumps the generation and runs with `queue.sync`; deactivation records the generation, runs with `queue.async`, and skips itself if the generation has moved. Video and audio cards (`RichAudioPlayer`) were the only other code that set the category and activation directly; they now go through `VoiceAudioSessionCoordinator.activateForCardPlayback()` / `deactivateAfterCardPlayback()` onto the same queue. Their "owned elsewhere" guards are unchanged and cards still hold no lease. The coordinator's lease bookkeeping and the `VoiceAudioSessionControlling` protocol are unchanged. `scripts/test-timings.json` gets a baseline for the new test class so `plan-tests.py validate` still passes.

Credit: the idea comes from Marceswan's "Serialize AVAudioSession activation on a dedicated queue", https://github.com/Marceswan/hermes-conduit/commit/7f80220e. His patch edited per-service call sites (`AVAudioCaptureService`, `AVSpeechPlaybackService`) that no longer touch the session upstream, so the idea moved into the one seam all changes now pass through. New compared with his version: the generation guard that drops a stale deactivation (his relied on FIFO order only, which is correct but still flaps the session), routing the media cards through the queue, and the fake-backend tests. His unrelated `assign(from:count:)` change was not taken.

Review notes: upstream's coordinator is already ordering-safe while every call is synchronous; the ordering problem only appears once deactivation leaves the main thread, which is why the same-queue rule and the generation guard come with it. Activation still blocks the main thread as long as before, in his version and here; making it async would mean an async `acquire` across every audio service. Reviewing the coordinator found a race the port had to close: a media card started right after Read Aloud stops would activate `.playback` outside the queue, and the still-queued deactivation would then cut the card's sound. Routing cards through the queue fixes it. CallKit's `configureForIncomingCall()` calls `setCategory` (sync, bumps the generation) before `action.fulfill()`, so a pending deactivation can't hit the call's audio. A failed deactivation is now logged on the queue instead of thrown back; the coordinator clears its applied policy anyway, so nothing goes stale.
