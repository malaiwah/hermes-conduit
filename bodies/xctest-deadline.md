Before: the lane runner's watchdog (`run_with_deadline` in `scripts/ci-lib.sh`, used by `ci-test-lane.sh` and the Mac gate) only moved to the finalize grace once the batch's whole test budget had run out, and it only recognised the end of the session from xcodebuild's own `** TEST EXECUTE SUCCEEDED/FAILED **` line, which xcodebuild prints after finalizing. A batch whose tests had all finished but whose finalize step hung (writing the xcresult, a simulator diagnostics request) used up the rest of its budget, at least 600 s, before it was killed, and the batch retry did the same again.

After: XCTest's top-level suite summary (`Test Suite 'Selected tests' passed/failed at …`, or `'All tests'` for an unfiltered run) also counts as the end of the session. As soon as either marker shows up, the deadline becomes now + `XCODEBUILD_FINALIZE_GRACE_S` (180 s by default), so a hung finalize costs at most the grace, and a session ending close to its budget still gets the full grace.

How: `log_has_terminal_result_marker` also returns true when the last top-level suite line is `passed` or `failed`; class- and bundle-level summaries don't count. `run_with_deadline` checks the marker on every poll instead of only when the budget runs out; on the first match it sets the grace deadline, and if the marker stops matching (a retry iteration printed a new `started` line) it restores the original budget deadline. A batch still runs at most budget + grace, the exit status is still the only verdict, a timeout is still 124, and the kill message now says whether the grace or the budget ran out. `docs/CI.md` and the `ci-lib.sh` header are updated. Hosted CI calls `xcodebuild` directly and doesn't use `run_with_deadline`, so it is unaffected; neither are the `resolve` and `build-for-testing` steps, whose logs never print these markers.
