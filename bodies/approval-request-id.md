Before: a card without a request id (the one a push restores, and every card from a gateway that predates request ids) was answered with `approval.respond { choice, session_id }`, and Hermes settled the oldest approval queued in that session. With two approvals queued, Run on the push card for "Delete the build folder?" could run the other, older command.

After: answering such a card first reads `approval.pending` for its session. When the gateway names its requests, the answer carries the `request_id` of the queued request whose explanation the card shows (and whose command, when the card has one; a push card has none). When nothing matches, nothing is sent and the card reads "This approval is no longer active." When several match but run different commands, nothing is sent and the queue's own cards, each with its command, replace it.

How: `legacyApprovalTarget(for:using:profile:)` reads the queue through the same `ChatResumeLifecycleOperations` seams the refresh uses, and a static `legacyApprovalTarget(for:in:)` holds the matching rule. The explanation is compared the way the notifier sends it: whitespace collapsed and cut at 500 code points with no ellipsis, so a card whose text reaches the cut matches the queued request it begins. A redacted push carries the notifier's placeholder ("Hermes needs your approval. Open Conduit for details.", kept in `AppState.redactedApprovalPushDescription`); it is answered when exactly one request is queued, and otherwise sends nothing and lets the refresh show the real cards. A gateway that names no request ids, or has no `approval.pending` (-32601), is answered by session as before. Any other failure to read the queue (timeout, connection) sends nothing and leaves the card in its retryable error state; it never falls back to the session-wide answer. The ownership fence (profile, client identity, decision key) is checked again after the queue read, before anything is sent. The voice-call answer goes through the same function and benefits too. No new strings.

Review notes: the notifier's text rules (whitespace collapse, 500-code-point cut, redaction placeholder) are mirrored in two constants with a comment pointing at the notifier. If the notifier changes, push cards read "no longer active" or get refreshed instead of answering the wrong request, which is the safe way to fail. A prefix match can't tell apart two queued requests whose explanations share their first 500 characters; if they run different commands, that is the ambiguous case and nothing is sent.
