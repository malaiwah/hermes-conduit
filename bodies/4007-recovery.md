Before: on a cold launch the app shows the read-only saved copy and resumes the saved conversation. When the session catalog still lists that conversation but `session.resume` answers 4007 ("session not found"), the automatic resume only scheduled a reconnect, so it retried the same dead row forever behind the saved copy ("Failed to restore this conversation"). The missing-session recovery only ran when the saved session was absent from the catalog, and it stopped with nothing scheduled when its fallback row was dead too.

After: a listed session that answers 4007 is first resumed once by its stored id (Hermes drops runtimes and resumes by the stored id, #446), so a runtime id reaped by a gateway restart is not treated as a dead conversation. Only when the stored id also answers 4007 is the row dead: the app forgets the saved pointer, opens the next catalog row, and after at most three more dead rows (or when none is left) creates a fresh chat.

How: a 4007 on a row whose stored id differs from the id resumed is retried by the stored id with the same accepted ids and identity. Dead rows go through one path that drops the saved pointer and its agents, walks the catalog, and finally creates a new chat with the turn marked as synchronizing, so New Chat waits for that create. Rows found dead are remembered per dashboard and profile for the run, so a retry after a failed create doesn't probe them again. A transient failure is not evidence that a row is dead: it keeps the usual retry and creates nothing. Every step re-checks the sync's ownership fences (automatic intent, viewport transition, reconciliation, profile, client). The tests needed one behaviour-neutral seam: `ChatResumeLifecycleOperations.createSession` replaces the automatic resume's `session.create` when set. New Chat needed no change, since `canTapNewChat` already lets it queue while connected with the saved copy up (#711); a test pins that.
